# flipp Work Ledger constraint acceptance matrix

Version 0.1 · 8 October 2026 · For review

## How to read this document

This matrix turns product boundaries into stable, testable release criteria. An **accepted design constraint** means the requirement is part of the intended design. It does not mean code exists, a deployment is authorized, or proof has passed.

Current state for every hard constraint below: **accepted in design; not implemented; proof not run**. Proposed pilot parameters remain proposals. No row authorizes deployment, spending, credentials, persistent access, or private data.

Status may advance only through these values:

1. `design-accepted` — the requirement and proof are agreed in documentation.
2. `implemented-unverified` — an implementation exists, but required proof has not passed.
3. `verified` — the named automated and integration proof passed against an identified build and environment.
4. `exception-approved` — the owner explicitly accepted a documented, time-bounded exception and residual risk.

Release gates fail closed. Missing evidence, an unknown result, or an expired exception is not a pass.

## Guarantees the ledger cannot make

The following remain assistant- and external-system risks even if every ledger test passes:

- **External authority:** the ledger can record referenced scope but cannot decide that a third-party action is legally, contractually, or currently authorized. The assistant must check at action time.
- **External truth:** the ledger can validate evidence presence, authorship, and revision consistency but cannot independently know that an external result is true.
- **At-most-once external effects:** idempotency and fencing protect ledger writes. They cannot guarantee that an arbitrary external service executed an action only once, especially after a timeout or lost response.
- **Environment availability:** “no subsequent task check recorded” does not prove whether a Mac, cloud executor, network, or integration is online.

Required mitigation is an explicit assistant protocol: check current authority, use an external idempotency mechanism when available, reconcile ambiguous results read-only, block blind retries, and record uncertainty. Integration tests can reduce risk but cannot turn these boundaries into ledger guarantees.

## Proof register

No implementation proof has been run. When work is separately authorized, record each proof with the constraint ID, build commit, environment, test artifact, time, and result. Never mark a constraint `verified` from a document review, unit test alone when an integration test is required, or a callback `2xx` without the full current-task fetch loop.

An exception record, if explicitly approved, must name the constraint, reason, owner, affected build and environment, compensating control, expiry, and rollback or remediation plan. C01, C03, C04, C07, and C10 should be treated as non-waivable for a private pilot because violating them changes the product's authority or privacy boundary.
